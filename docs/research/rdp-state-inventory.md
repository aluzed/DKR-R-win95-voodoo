# Inventory of the RDP state — state as of 14 August 2026

> **This inventory is incomplete, and deliberately so.** It records what is
> established and names what is not. A plausible inventory would be more dangerous
> than a partial one: a missed configuration does not show at decoding time, it
> shows on screen, as a surface of an unexpected colour, possibly in a single
> level.

## What is established

### The decoding is verified against the decomp's headers

The 63 `G_CC_*` macros in the neighbouring native port's headers are resolved,
encoded with the real `GCCc*w*` macros, then decoded: **all 63 come back field for
field**, on both cycles.

The vectors are generated by `tools/win95/gen_combiner_vectors.py` and not
transcribed by hand. That distinction is what gives the test its value: a
transcription goes wrong silently, and the test would then share the error of the
code it checks.

### A trap the generator revealed, and which holds for E05-S03

**The field widths are not uniform, and that changes the value.**

| Field | Width | `G_CCMUX_0` is there |
|---|---:|---:|
| `a`, `b` (RGB) | 4 bits | **15** |
| `c` (RGB) | 5 bits | **31** |
| `d` (RGB) | 3 bits | **7** |
| alpha | 3 bits | **7** |

`G_CCMUX_0` is defined as 31. It fits in `c`'s five bits, not in `a`'s four — the
hardware stores 15 there. A first version of the generator emitted the raw value
and the test accused the decoder, **which was right**.

A consequence to remember: the same symbolic `0` is not encoded the same way
depending on the position. A mapping table written on the names rather than on the
values would go wrong.

### The canonical form

A 64-bit key, fields at fixed positions, without compression: two distinct
configurations cannot collide — verified on all 63 — and a key can be read back by
hand.

**The cycle mode is part of it**, and that is not a detail: the same combiner word
in one cycle and in two does not produce the same image, the second stage not
being evaluated in the first case. Conflating them would give a table that returns
the wrong image without ever complaining.

### The translation announces itself when it is approximate

E04-S01's abstract state has four combination modes; the RDP has an infinity of
them. The translation returns the closest mode and sets `exact = 0` in two cases:
**two texels read** — which require two TMUs or a second pass — and **the two-cycle
mode**.

An approximate translation that does not announce itself produces a plausible,
wrong image. That is the worst possible result for a port whose oracle is the
image.

## What is not established

### The inventory of the 33 configurations is not rechecked here

The ticket asks for it to be rechecked on this port — "the inventory is a solid
starting point, not an imported truth". **That is not possible by the same
method.**

The neighbouring port derived it from the decomp's **C sources**, by resolving the
macros in the settings tables. This port does not have those sources: it works
from recompiled MIPS, and `extern/dkr-decomp` is absent. Its equivalent is
run-time instrumentation — the ticket's step 6 — which requires a complete game,
hence the ROM.

The neighbour's figures, for the record:

| | Configurations | Entries |
|---|---:|---:|
| from the settings tables | 21 | 193 |
| emitted outside the tables | 12 | 22 |
| **consolidated total** | **33** | |

| Texels read | Configurations | Consequence on the target |
|---:|---:|---|
| 0 | 8 | no texture — 1 TMU unused |
| 1 | 22 | 1 TMU suffices, a single pass |
| 2 | **3** | 2 TMUs, or a second pass on single-TMU hardware |

The three two-texel ones are `BLENDTEX_PRIM`/`MODULATEIDECALA2` (32 entries,
flashing lights), `BLENDT_ENV_ALPHA_A_T1xP`/`PASS2` (the font) and
`BLENDTEX_MODULATEA_1_PRIM`/`BLENDI_ENV_ALPHA_MODULATEA2` (waves).

### The table of known configurations is primed, not complete

`rdp_state.c` catalogues eight configurations whose exact composition is known.
`dkr_rdp_combiner_name` returns `NULL` for everything else, and **it is that
signal that counts** while awaiting the instrumentation.

### Frequency and screen area: absent

The criterion asks, per configuration, for the frequency and the screen area
covered — which decides the order of work in E05-S03. Both are measured at run
time. The neighbour's count of table entries is a crude substitute for them: it
counts declarations, not pixels.

## Modes decoded outside the combiner

| Field | Source | Decoded |
|---|---|---|
| cycle mode | `othermode_h` bit 20, 2 bits | 1 cycle, 2 cycles, copy, fill |
| filtering | `othermode_h` bit 12, 2 bits | point (0), bilerp (2), average (3) |
| LOD, detail, texture perspective | `othermode_h` 16, 17, 19 | yes |
| alpha comparison | `othermode_l` bit 0, 2 bits | yes |
| Z source | `othermode_l` bit 2 | yes |
| depth test and write | `othermode_l` bits 4 and 5 | yes |
| blender | `othermode_l` >> 3 | kept raw — belongs to E05-S05 |

`G_TF_AVERAGE` is 3 and **there is no value 1**: treating the field as a boolean
would give bilinear filtering for `AVERAGE`, which is almost right and therefore
hard to see. The decoder distinguishes them, and the suite verifies it.
